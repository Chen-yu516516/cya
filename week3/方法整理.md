## 一、四个阶段

```
招股书 Markdown → raw → parsed → validated → reviewed(*.xlsx)
```

| 阶段 | 干什么 | 脚本 | 输入 → 输出 |
|------|--------|------|------------|
| **raw** 原始提取 | 正则定位"历史沿革"章节 + 表格正则抽事件，保留原文数值不做处理 | `week3/pipeline/week3_pipeline.py` | Markdown → `pipeline/stages/raw/*.jsonl` |
| **parsed** 结构解析 | 字符串转数字、单位归一化（股→万股）、字段映射、缺失价格反算 | `pipeline/stages/migrate_stages.py` | raw → `parsed/*.jsonl` |
| **validated** 校验标记 | schema 校验（必填/范围）+ cross-check 标记，只标问题不改数据 | `migrate_stages.py` + `validation/cross_check/per_event_check.py` + `per_shareholder_check.py` | parsed + comparison.csv → `validated/*.jsonl` |
| **reviewed** 人工复核 | 人工对照 PDF 逐条核实修正，**所有人工修改只发生在这里** | 无脚本 | validated → `reviewed/*.xlsx`（即 final/ 8 家） |

**关键点**：
- 前三个阶段全自动可复现，跑 `migrate_stages.py` 结果一致。
- 单位归一化判据：`evidence_text` 含"（股）"列标题 且 `subscription_shares_wan > 100000`（阈值 `UNIT_ERROR_THRESHOLD`），命中自动 ÷10000 并打 `_unit_corrected` 标记。
- reviewed 阶段每次人工修改必须留四列：`original_value` / `revised_value` / `reason` / `pdf_page`。

```bash
cd week3/pipeline/stages && python3 migrate_stages.py
cd week3/validation/cross_check && python3 per_event_check.py && python3 per_shareholder_check.py
```

## 二、常见错误与真实案例

### 1. 单位搞混（股 vs 万股）— 赛分科技（688758）

2021-10-28 增资批次的 `subscription_shares_wan` 填的是股数：源峰磐赛填 `1,571,815.0`，实为 `157.1815` 万股，差 10000 倍，同批 10 条全中招。

- **怎么发现**：pipeline 大值告警（`>100000` 报 WARN）；cross-check 逐事件差额 `-1571815.0000 万股`，数量级一眼看出是单位问题。
- **怎么修**：`week3/data/fix_saifen_units.py` 逐条 ÷10000。判据：有效万股不可能超 1000（8 家最大单笔 ~623 万股），`>1000` 即触发。

### 2. 股东名字简写对不上 — 三协电机（920100）

人工写"稳正景明"，自动化搬全称"深圳市稳正景明创业投资企业（有限合伙）"，长度差 10 倍指同一实体。星图测控"四方股份" vs "北京四方继保自动化股份有限公司"同理。6/8 家都有。

- **怎么发现**：Auto vs Gold 对比时名称字符串不匹配，match 率被拉低。
- **怎么修**：建简写-全称对照表，或对比时用编辑距离/前缀模糊匹配，先确认"是同一股东"再比字段。

### 3. 事件漏提取 — 股权转让系统性缺失（6/8 家）

自动化事件分类只分了"增资"类，没有"股权转让"类，8 家 JSONL 里 `equity_transfer` 一条都没有，但 Gold 里已有人工标注的转让数据。

- **怎么发现**：cross-check 转让事件全空；对比发现 Gold 有转让而 JSONL 无对应记录。
- **怎么修**：`week3/fill_equity_transfers.py` 从 manual_gold 的"4_股权转让"Sheet 提取，转成 `equity_transfer` JSONL 补进 `data/`。

**相关案例**：星图测控时点不足——招股书是概述性文字（"2021 年 3 月至 8 月经历数次股权转让"）无结构化表格，只提取到 3 个时点。属数据源颗粒度问题，Gold 标注为已知限制，不主观补全。

## 三、Cross-check 逻辑

### 逐事件（per_event_check.py）

核心等式：`前快照 + 事件变动 = 后快照`，容差 `TOLERANCE = 0.01`（万股）。

1. 读 `subscription_flow` + `equity_snapshot`，按时间排序。
2. 每个增资事件：找事件前最近快照（before）和后最近快照（after），验 `before持股 + 增资量 = after持股`。
3. 每个转让事件：转让方 `before - 转让量 = after`，受让方 `before + 转让量 = after`。
4. 结果写 `cross_check_results/per_event_check_report.csv`，每条带 PASS/FAIL/WARN/SKIP + mismatch_reason。

判定：差额 <0.01 → PASS；超容差 → FAIL（写明差额）；新增股东后快照找不到 → WARN；缺前后快照 → SKIP。

注意：快照定位是简化逻辑（按 t0/t1/t2 顺序），适合快速定位数量级异常，不当最终结论。

### 逐股东（per_shareholder_check.py）

核心：每个股东持股轨迹必须连续，跳变要有事件解释。检查三类异常：

1. **持股跳变**：相邻快照变化 >50%（`JUMP_THRESHOLD=0.50`）且无对应增资事件。
2. **股东凭空出现**：t_i 出现但 t_{i-1} 不存在，且无增资事件引入。
3. **股东消失**：t_{i-1} 存在但 t_i 消失（当前无条件标记，有误报，人工看 detail 判断）。

流程：每家公司按时点分组快照 → 每个股东建时间线 `[t0, t1, ..., tn]` → 逐段检查 → 写 `per_shareholder_check_report.csv`。

```bash

# 2. 两条 cross-check 线

# 3. 看报告，FAIL/异常逐条对照 PDF 人工复核，修改留四列记录
```
