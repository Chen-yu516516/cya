## 三、Pipeline 自动化程度评价

### 3.1 当前 Pipeline 能力

```
输入: week3/data/*.jsonl (管道原始输出)
  ↓
Schema 校验（类型/必填/数值合理性）
  ↓
输出: auto_excel/（双 Sheet Excel）
输出: auto_jsonl/（原始副本，无任何修正）
输出: validation.log（校验日志）
```

**一句话评价**：Pipeline 能自动完成「搬运 + 格式转换 + 基础校验」，但**不能自动完成「数据修正」**。

### 3.2 自动化 vs 人工修正差距

| 操作 | 自动化 | 人工 |
|------|--------|------|
| JSONL → Excel | ✓ | — |
| Schema 类型校验 | ✓ | — |
| 必填字段检测 | ✓ | — |
| 数值合理性告警 | ✓（检测到 8 条 unit 异常） | — |
| 单位归一化 (股→万股) | ✗ | ✓（fix_saifen_units.py） |
| 跨页表格拼接 | ✗ | ✓（人工逐页比对） |
| 反推值标注 | ✗ | ✓（在 notes 中标注） |
| 时点序号一致性 | ✗（检测） | ✓（手工调整） |
| 股权激励分类 | ✗ | ✓（在 notes 中区分） |

## 四、Auto vs Gold 对比核心结论

### 4.1 差异来源分析

183 条差异记录的来源分布：

```
手工修正（Gold 侧主动修改）:  ~120 条 (65.6%)
   - 三联锻造：出资额/股本单位转换
   - 友升股份：出资额重新计算
   - 赛分科技：股权结构大规模调整
   - 影石创新：股本单位调整

数据缺失（原文未披露）:      ~35 条 (19.1%)
   - 云汉芯城：34 条 subscription_amount_wan null

单位错误（未归一化）:        ~10 条 (5.5%)
   - 赛分科技：10 条 subscription_shares_wan

反推值添加（notes 级别）:    ~10 条 (5.5%)
   - 三协电机：持股比例反推（数值本身无差异）

其他:                        ~8 条 (4.4%)
   - 黄山谷捷/星图测控小额差异
```

### 4.2 差异密集字段

| 排名 | 字段 | 差异次数 | 根因 |
|------|------|---------|------|
| 1 | total_shares_wan | 98 | 股本单位/口径不一致 |
| 2 | shares_held_wan | 77 | 同上 |
| 3 | capital_contribution_wan | 71 | 出资额计算方式不同 |
| 4 | total_capital_wan | 56 | 同上 |
| 5 | shareholding_ratio | 36 | 赛分科技股权激励 |
| 6 | subscription_shares_wan | 22 | 单位错误 + 手动调整 |
| 7 | subscription_price_yuan | 22 | null vs 有值 |

### 4.3 关键洞察

1. **赛分科技是 Pipeline 的「边界案例」**：0% 匹配率意味着 提取模块 原始提取对此公司几乎完全不可用，是未来改进的最高优先级目标。

2. **三协电机是 Pipeline 的「理想案例」**：100% 匹配率证明当招股书格式规范、表格清晰时，管道提取可以达到 Gold Standard 质量。

3. **出资额/股本是差异重灾区**：这两个语义相关的字段贡献了超过 60% 的差异，说明 Gold 在构建过程中对历史沿革中的资本演变做了系统性的重新梳理，而 提取模块 的逐页提取无法把握这种全局演变。

## 五、规则覆盖与 指令 设计评估

### 5.1 规则提取可行性

| 等级 | 公司 | 规则可提取比例 |
|------|------|--------------|
| 高 | 三协电机、黄山谷捷 | 85-95% |
| 中 | 云汉芯城、影石创新 | 50-70% |
| 低 | 星图测控 | 40-50% |
| 极低 | 三联锻造、友升股份、赛分科技 | <30% |

纯规则提取的 F1 估算：**~54%**（精确率高但召回率低）。

管道辅助提取的 F1 估算：**~72%**（召回率显著提升但精确率受 unit 错误拖累）。

混合方案（规则+提取模块+人工）的 F1 估算：**~92%**（当前 Gold Standard 水平）。

### 5.2 指令 设计核心发现

| 发现 | 严重程度 | 改进优先级 |
|------|---------|-----------|
| 处理管道道不执行算术转换（/10000） | P0 关键 | 最高 |
| 逐页独立提取导致跨页表格断裂 | P1 重要 | 高 |
| 指令 对股权激励无区分规则 | P2 改进 | 中 |
| Few-shot 示例缺失，纯文字描述转换规则效果差 | P1 重要 | 高 |
| 原文逐字引用约束执行完美 | — 保持 | — |

## 六、已知限制与改进方向

### 6.1 当前限制

1. **赛分科技的大规模差异**（73 条/326）说明当前 处理管道道提取对该公司的覆盖严重不足，可能原因包括：招股书版本、表格呈现方式、或股权结构本身的复杂性。

2. **单页视角的全局信息丢失**：时点命名、出资额计算、跨页表格拼接等问题都根源于逐页独立提取的架构。

3. **提取模块 的算术能力缺陷**：单位转换（/10000）、比例反推等需要计算的操作不应放在 处理管道道层。

4. **无自动修复机制**：Pipeline 能检测问题（validation.log 中的 WARN）但不能自动修复。

### 6.2 短期改进（1-2 周可实施）

| 改进项 | 方法 | 预期效果 |
|--------|------|---------|
| Unit auto-fix | Pipeline 后处理检测 shares > 100000 → /10000 | 修复赛分科技 10 条 |
| 跨页上下文 | 双页合并发送 + 后处理合并连续表格 | 修复三联/友升/赛分部分差异 |
| 时点自动排序 | 提取 time_point 中的日期 → 排序 → 重新编号 | 消除时点编号不一致 |
| 股权激励识别 | 关键词检测（「激励」「持股平台」）→ 单独分类 | 降低股权存量 Sheet 噪点 |

### 6.3 中期改进（1-2 月）

1. **Few-shot 指令 优化**：在 指令 中嵌入 2-3 个完整输入→输出示例，覆盖单位转换、跨页表格、非标格式场景。
2. **表格专用提取器**：对结构化表格使用 Camelot/Tabula 直接解析，对非结构化文字使用 提取模块。
3. **自动校对闭环**：Pipeline 输出与 Gold 做字段级 diff，对不一致项自动标记供人工审核。

### 6.4 长期方向

1. **多模态视觉提取模块**：直接对 PDF 表格截图做视觉理解，跳过文本解析环节，解决表格跨页和格式丢失问题。
2. **增量更新框架**：当招股书有更新版本时，仅重新提取变更部分，保留已校验的存量数据。

## 七、对下次任务的建议

### 7.1 数据层面

1. **统一 gold JSONL 的存储策略**：当前 week3/data/ 中的 JSONL 为修正前版本，gold 修正在 Excel 中。建议在 data/ 或独立目录中存储**修正后的 gold JSONL**，方便自动化对照。

2. **记录修正 diff**：每次手工修正写入一个 `fix_log.json`（字段路径 + 旧值 + 新值 + 原因），形成可审计的修正链。

### 7.2 工程层面

1. **Pipeline 配置化**：将公司列表、字段映射、修正规则从脚本中抽取到 YAML/JSON 配置文件，降低维护成本。

2. **增加 CI 检查**：对每次 pipeline 运行做自动化断言：
   - `total_records >= 预期值`
   - `schema_errors <= 阈值`
   - `saifen_unit_warnings == 8`（已知的）

### 7.3 分析层面

1. **逐字段精度 vs 召回分析**：不仅看整体匹配率，还要分字段统计精度和召回率，更能定位问题。

2. **招股书元数据分析**：统计每家招股书的表格数量、跨页比例、单位标注方式等元数据，作为提取难度的事前预估指标。
