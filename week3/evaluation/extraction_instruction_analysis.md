## 二、指令 要素逐一分析

### 2.1 单位要求（万股/万元 vs 股/元）

**指令 原文**：
> *若原文写"1,571,815 股"，需转换为 157.1815 万股*

**实际执行效果**：❌ 显著失败

| 证据 | 说明 |
|------|------|
| 赛分科技 10 条 flow 记录 | `subscription_shares_wan` 均未转换，直接填入原始股数 |
| 三联锻造 12 条差异 | 部分字段涉及单位问题 |
| 其他 6 家公司 | 未见明显单位错误 |

**根因诊断**：
1. **指令 中的示例不够「可视」**：仅用文字描述转换规则，缺少带箭头的视觉化对比（如 `1,571,815 股 → 157.1815 万股` 的直接示例表）
2. **表格列标题的干扰**：当  看到列标题「认购股份（股）」时，倾向于逐字照搬，而非执行额外的数值转换
3. **转换运算的非确定性**：`/10000` 是一个算术操作，处理管道 在文本生成中不擅长执行精确算术

**改进建议**：
- 在 指令 中提供 **few-shot 完整示例**：一行原始 JSON 输出 + 一行修正后输出
- 在 Pipeline 中增加后处理规则：检测 `shares_wan > 100000` 自动除以 10000

**敏感性评分**：★★★★★（最敏感，直接影响 10 条记录的正确性）

---

### 2.2 多页表格合并指令

**指令 原文**：
> *如果当前页面无相关数据，输出空*

**实际执行效果**：⚠️ 部分问题

**问题表现**：
- 招股书股权结构表常跨越多页， 对每页独立处理
- 连续页面的同一表格可能被识别为不同时点/不同批次的独立记录
- 三联锻造、赛分科技各有数十条差异部分源于此

**根因诊断**：
1. **逐页独立提取的架构缺陷**：当前方案将每页单独发送给 处理管道，处理管道 看不到相邻页的上下文
2. **无跨页锚点机制**：缺乏"此表格接上一页"的提示信号
3. **指令 缺少「跨页待续」的指令**：未要求 处理管道 在检测到表格断裂时输出特殊标记

**改进建议**：
- 改为**双页合并发送**：将相邻两页一并发送给 处理管道，提供上下文
- 在 指令 中增加「如果表格跨页，请注明"接下一页"」的元指令
- 在 Pipeline 后处理中合并相邻页面的连续表格

**敏感性评分**：★★★★☆（高敏感，影响三联/友升/赛分三家公司的匹配率）

### 2.3 股权激励表格过滤效果

**指令 原文**：
> *股权结构存量 = 某一时点公司的完整股权分布*

**实际执行效果**：⚠️ 部分失败

**问题表现**：
- 三协电机第 2 批 15 名员工激励对象的表格被  纳入 `equity_snapshot`，而非单独分类
- 影石创新的期权激励表格混入股权结构（28 条差异）
- Gold Standard 中这些记录仍保留在 `equity_snapshot` 中（因为历史股权结构确实包含这些股东），但属于特殊类别

**根因诊断**：
1. **指令 对股权激励无显式排除规则**：未说明「员工持股平台 / 股权激励对象」是否应单独分类
2. **定义模糊**：股权激励对象在历史上确实是股东，指令 未提供区分标准
3. **视觉相似性**：股权激励表格与普通股权结构表格格式相同

**改进建议**：
- 在 指令 中增加 `record_type` 的第三类：`equity_incentive`，将员工持股计划单独分类
- 在 `notes` 中标注「员工持股平台」
- 在 `equity_structure_scope` 中区分「普通股」与「期权/限制性股票」

**敏感性评分**：★★★☆☆（中等敏感，影响分类精度但不影响数值准确性）

### 2.4 原文证据必须逐字引用

**指令 原文**：
> *evidence_text: 逐字引用的原文证据（必须从 PDF 原文中摘录）*

**实际执行效果**：✓ 良好

| 证据 | 说明 |
|------|------|
| 所有 731 条记录 | evidence_text 均包含大量原文摘录 |
| 赛分科技 | 原文包含完整表格数据（列标题+数值），为 unit fix 提供了判断依据 |
| 未发现 | 概括性改写或编造的 evidence_text |

**评估**：这一约束被  严格遵循，是 指令 中最成功的部分。原文证据的完整保留为后续手工验证和自动修复提供了不可替代的审计线索。

**敏感性评分**：★★☆☆☆（低敏感，表现良好）

### 2.5 时点命名规范（t0/t1/...）

**指令 原文**：
> *time_point: 严格使用 t0/t1/t2... 的递增序号*

**实际执行效果**：⚠️ 中等

**问题表现**：
- 星图测控仅 3 个时点（t0/t1/t2），实际应有更多
- 赛分科技 Gold 中时点编号经过大幅手工调整

**根因诊断**：
1. **时点识别依赖于对历史沿革的整体理解**：逐页处理的方式无法掌握全局时间线
2. **编号冲突**：不同页面中的表格可能被赋予相同的 `time_point`
3. **缺少全局排序步骤**：Pipeline 中未对提取出的时点按时间排序后重新编号

**改进建议**：
- 在 Pipeline 中增加后处理：按 `time_point` 中的日期字符串排序，自动重新分配 t0/t1/...
- 在 指令 中要求 处理管道 使用带日期的描述性时点名称（如 `t1/2021-03-15`），便于后续排序

**敏感性评分**：★★★☆☆（中等敏感，影响时点序列的一致性）

**指令 原文**：

## 三、指令 设计综合评估

### 3.1 整体有效性矩阵

| 指令 要求 | 执行效果 | 是否需改进 | 优先级 |
|------------|---------|-----------|--------|
| 单位归一化（股→万股） | ❌ 失败 | 是 | P0 |
| 逐字引用原文 | ✓ 成功 | 否 | — |
| JSONL 格式输出 | ✓ 成功 | 否 | — |
| Schema 字段完整性 | ✓ 成功 | 否 | — |
| 多页表格合并 | ⚠️ 部分失败 | 是 | P1 |
| 股权激励过滤 | ⚠️ 弱 | 是 | P2 |
| 时点命名规范 | ⚠️ 中等 | 是 | P2 |
| 空值使用 null | ✓ 成功 | 否 | — |

### 3.2 最高优先级改进

**P0: 单位归一化强化**

当前 指令 的问题不在于「没说清楚」，而在于 管道不擅长执行算术转换。改进方向：
1. 在 指令 中提供 Few-shot 完整示例（原始输入 → 正确输出）
2. **不依赖 处理管道 做转换**，改为 Pipeline 后处理规则：
   ```python
   if evidence_text contains "（股）" and shares_wan > 100000:
       shares_wan /= 10000
   ```

**P1: 跨页表格上下文**

将逐页独立发送改为**双页窗口发送**，或在 Pipeline 后处理中对连续页的相同 `subscription_date` / `batch_label` 进行合并。

### 3.3 指令 设计的核心教训

1. **管道不擅长数学运算**：不要期望 处理管道 在输出中执行单位转换、比例计算等算术操作。这些应放在 Pipeline 后处理。
2. **单页视角的局限性**：逐页提取必然导致全局信息丢失，需要在后处理阶段重建全局视图。
3. **Few-shot 示例比规则描述更有效**：相比于"若原文写XXX，需转换为YYY"的文字描述，直接给出输入→输出的完整示例更易被 处理管道 内化。
